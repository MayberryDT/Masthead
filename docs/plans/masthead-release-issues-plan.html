P0 — Settings save hangs; dossier won’t open; contradictory enrichment state

Settings Daemon Now / Dossier

Production: “Saving…” on provider for a long time; after save, board still shows offline badges; dossier modal fails; remote toggle appears stuck on.

Anchors
POST /settings/llm-provider → 202 + getSettingsState (server.ts 2144–2150); renderer OperationsPanel.tsx + useSettingsDataController.ts (duplicate save paths); dossier GET /sessions/:id/dossier + SessionDetailModal / useBoardSessionDetailController.ts; connection gating App.tsx effective live vs settings base URL.
Hypothesis
Slow or blocking save (provider model list fetch, large JSON body, or UI never clearing saving on error); separate regression: projection URL / collector offline while settings POST succeeds → dossier fetch errors masked as “offline” cards.
Risk
Duplicate save paths (OperationsPanel vs useSettingsDataController) diverge; bridge read-only rejects writes but dossier GET should work.
Rollback
Revert UI save coupling; user clears provider via existing clear-key; env MASTHEAD_REMOTE_ENRICHMENT=0 emergency.
  1. Reproduce with Electron Dev + daemon: save OpenRouter-compatible provider; time POST /settings/llm-provider and confirm 202 body matches remoteEnrichmentEnabled.
  2. Trace EnrichmentSettings.tsx save(): ensure finally clears saving; surface daemon 400 errors; avoid requiring “Save provider” to flip remote-only intent.
  3. While saving, verify dossier GET still uses activeProjectionUrl from connection provider (not stale bridge).
  4. After save, refresh settings state in UI from response; do not rely on local remoteEnabled if server disagrees.
  5. Add regression test in settingsApi.test.ts for toggle off + credentials retained; optional UI test for save timeout/error path.

Verify: Toggle off persists after reload; dossier opens for a known session; board offline badges track headline mode (Thread A), not remote enrichment (Thread B).

1 — Notify when a session leaves active (→ idle / blocked / ended)

Electron Now Preferences

Green/active state on the board is visible; transition to idle or blocked has no OS-level notification.

Anchors
Lifecycle from sessionReducer.ts / card sessionStateClassName in SessionCard.tsx; no Notification API in src/ today; IPC pattern channels.ts, preload.ts, ipc.ts, main.ts; PreferencesSettings.tsx is device-local motion only (not daemon-backed).
Approach
Detect transitions in renderer on projection poll (App.tsx / live projection client): prior card lifecycle/primaryStatus map → compare each refresh. When desktop: mastheadDesktop.invoke new channel e.g. masthead:notify:session-ended implemented in main with Notification (Linux notification portal). Preference: new row in Preferences next to Motion — store in localStorage (same pattern as motionPreference.ts), default on in desktop, no-op in browser-only dev unless permitted.
Depends on
P0 stable projection polling.
Risk
Notification spam on flaky lifecycle; debounce per sessionId + ended transition only.
  1. Add ELECTRON_CHANNELS.showSessionNotification + handler in main.ts (title/body/sessionId); guard permission.
  2. Expose typed helper on window.mastheadDesktop in preload.
  3. Implement useSessionTransitionNotifications in app layer keyed off filtered board cards (respect user toggle).
  4. Extend PreferencesSettings.tsx with “Session ended notifications” toggle + short description (desktop only label).
  5. Unit-test transition detector with fixture cards; manual verify on Linux desktop build.

Verify (Electron desktop only — not in-app Browser): npm run dev:desktop; end or idle a live session → one OS notification; Preferences toggle off → silent. Vitest covers transition detector only.
