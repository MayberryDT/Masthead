Product frame

Masthead is not a control tower. It is the canonical session database.

The interface should help people collect, understand, search, and safely expose session history. Live observability is one view over that data, not the center of gravity for every surface.

1 Canonical session database

All imported harness history and live captures land in one local source of truth.

2 Logbook and search

The main way to find past work, inspect context, and recover session details.

3 Read-only MCP access

Agents can query history without mutating the local session store.

4 Live Now view

Useful current-state view, but not the template for every other page.

5 Source administration

Import, repair, and validate where the session history comes from.

Root causes

The same product problem is showing up in four different places.

The broken surfaces are not just visually busy. They are exposing implementation machinery before the user understands the job, the state, or the next action.

Advanced mode is the default

Diagnostics, raw tables, code blocks, status internals, and low-level rows appear before the plain user workflow.

Primary actions are unclear

Several surfaces show refresh, sync, repair, connect, copy, test, or delete without a clear first job.

Old card language lingers

The Sources area still feels like adapter inventory instead of a guided import and connection experience.

Everything competes visually

Cards, boxes, command rows, tables, and stat strips often have the same weight even when their importance differs.

States do not explain trust

Imported, connected, missing, syncing, and broken need human-readable proof, not just status badges.

Surface archetypes blur

Now, Sources, Agent Access, Settings, and Dossier should share style, but not the same layout logic.

Surface problem

Sources needs to become source setup, not adapter diagnostics.

The core job is conscious source setup: connect harnesses for live capture, optionally import past sessions, optionally import transcripts, optionally enrich them, and show transparent proof that the source is running.

What Tyler is seeing

  • The tab feels like a confusing pile of old cards and advanced data.
  • The no-data state should not expose secondary diagnostics as a peer action.
  • After Codex is imported, it is not obvious how to inspect that connection.

What the normal user path should explain

  • No data: one clear Set up sources CTA, not an import-only promise.
  • Live-only path: let Masthead start saving new sessions without forcing historical import.
  • Backfill path: let the user import past sessions after choosing harnesses and privacy scope.
  • Health path: show what each harness imported, what is running, and what still needs attention.

Surface problem

Agent Access should feel like setup and permission control, not a science-fiction console.

The user needs to know whether MCP is available, how to connect an agent, what that agent can read, and whether the connection has actually been used.

What Tyler is seeing

  • A full top command row exists mostly to hold one refresh button.
  • The page looks technical before it explains whether MCP works.
  • Code blocks, tool tables, and audit data compete with the basic setup job.
  • The MCP server may work, but the UI has not earned trust yet.

What the surface should make obvious

  • Connection status: MCP unavailable, ready, connected, or recently queried.
  • First action: connect Codex, Claude Code, Cursor, or a generic stdio client.
  • Permission boundary: read-only access and what data is included or excluded.
  • Proof: Codex can ask Masthead about the current project and receive useful context.

Problem statement for the next iteration

Agent Access should answer "Can my agent safely read Masthead, and how do I prove it?" The first successful moment is not a green badge. It is Codex using Masthead context in a real project conversation, with audit proof visible afterward.
Surface problem

Settings needs intent-based grouping and less visual weight.

The page has useful controls, but it currently asks users to parse storage, hooks, privacy, enrichment, and deletion as similarly important technical boxes.

What Tyler is seeing

  • Settings looks like the same sci-fi control panel pattern as the other weak surfaces.
  • There are too many cards and boxes without a clear hierarchy.
  • A large toolbar or header area exists for very few actions.
  • Database and runtime details compete with actions users understand.

What the page should organize around

  • Connections and capture: hook status, endpoint, install/test actions.
  • Privacy and data boundaries: retention, raw copies, exclusions, project scope.
  • Storage and portability: database location, exports, local files.
  • Advanced and danger: runtime details and deletion behind unmistakable hierarchy.

Problem statement for the next iteration

Settings should answer "How is Masthead configured, what data is kept, and what dangerous actions exist?" It should be calm, vertical, and grouped by intent instead of presenting every subsystem as a dashboard panel.
